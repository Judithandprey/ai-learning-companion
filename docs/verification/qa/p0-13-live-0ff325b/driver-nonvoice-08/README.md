## H1: the deadline reaches every in-flight operation, and the Windows runner's end is proven

**Runner.** The change is a runner-only delta (`runnerDeadlineDelta` in
[`qa_live_candidate.mjs`](../../../../../tests/e2e/windows/qa_live_candidate.mjs)), applied after the checker's
definitions are cut. Below it lies candidate 06's runner, byte for byte, and the checker is cut from that. The checker is
`9637db61…`, unchanged.
- `-WorkMs 320000` counts from the runner **process's creation** (`Get-Process -Id $PID`.StartTime, then its stopwatch),
  which is the moment its launcher spawned it. `-CloseMs 15000` gives the finally its own time.
- Every DevTools receive, send and connect, and every DevTools target-list HTTP request:
  - takes its bound (the time left) **before** the call starts;
  - is cancellable (`CancellationTokenSource`, `WebClient.CancelAsync`) and is cancelled at that bound;
  - if it times out after the deadline shortened it, or after the deadline passed, reports the deadline (`Stop-QaWait`).
- **Every effect that can follow a wait checks the time first:**
  - each DevTools command (in `Send-Cdp` and `Invoke-Cdp`);
  - the Edge and app `Start-Process`;
  - every window raise and front;
  - the `WM_CLOSE` post.
- **No loop swallows the deadline.** This covers `waitEval` (and a wait the deadline shortened reports the deadline) and
  both DevTools discovery loops. A deadline error in **any** step, required or not, aborts the run; it and every later
  step stay NOT_RUN.
- **Waits are limited by the time left:** sleeps, `closeApp`'s wait, and the finally's waits. `results.json` records
  `work_deadline`: the work and close allowances, the startup offset, and when the finally began.

**Wrapper.** After the native child, the Windows runner is checked first, by its **exact identity**:
- `powershell.exe` with exactly this invocation, created since the preflight, taken from the complete `powershell.exe`
  list;
- any other process that names this runner file is unresolved and is never signalled;
- the product-started checker is a different invocation, so it is foreign and never signalled.

It must be seen gone before the app and Edge cleanup. If it is still there, it is ended by that identity:
1. a close request first;
2. then an end through the process handle `signalCommand` holds, after rechecking the identity;
3. then a verification that it is gone.

The WSL launcher's exit is never taken as proof.

## H2: release blockers

`release_blockers` forbids any DISPLAY or ACCOUNT RELEASE claim when any of these holds:
- **The launcher** did not end cleanly by itself. That means any signal (including an outside SIGKILL before the
  ceiling), any error, a non-zero status or the ceiling.
- **The Windows runner's** end is not proven.
- **QA signalled the runner,** or any look or signal about it failed.
- The owned app and Edge are not confirmed gone.
- The connector is not seen released.
- The read-only watch was not seen ending.

Closed output is never taken as completion. Mechanics also require the runner's cleanup to be confirmed.

## H3: the watcher and the evidence

**The watcher.**
- [`qa_sub_watch.py`](../../../../../tests/e2e/windows/qa_sub_watch.py) takes `--max-seconds`; it keeps the 3600 s
  default for other callers. The wrapper sets it to the cleanup phase's end.
- `stop(ms)` joins this exact watcher within `ms`, also below 2 s: first its stop file, then SIGTERM, then SIGKILL. Each
  wait is bounded both by the clock and by the number of its sleeps.
- `watch_stop` records whether the stop was requested, any error, the signals and whether the watcher exited. A watcher
  not seen ending is a release blocker.

**The evidence.**
- [`run-status.json`](../../../../../tests/e2e/windows/qa_run_live_candidate.mjs), a small status record, is written
  first, before the collection.
- Every evidence read:
  - opens the file with `O_NOFOLLOW` and checks it with `fstat`;
  - reads through that open file, at most its size, and refuses a file that grows while read;
  - has a time check before it, as does every copy.
- Bounds:

  | What | Bound |
  | --- | --- |
  | Results | 16 MiB |
  | Live and admission records | 8 MiB each |
  | Each ask | 1 MiB |
  | Checker log | 8 MiB |
  | Watch log | 4 MiB |
  | Everything together | 64 MiB |
  | Capture folders | 8 |
  | Asks per capture | 64 |
  | Request IDs | 64 (strings only, deduplicated) |
  | Receipt launches | 8 |

- The receipt reader is time-checked per request.
- Copied abort text is limited to 2000 characters, and `run.json` is bounded by `reportText`, which falls back to the
  status record.
- Whatever is not read stays in the scratch and is reported as an explicit error.

## Remaining dependencies, stated, not relabelled

- **Reads that cannot be cancelled** are bounded only by the 360 s ceiling and the wrapper's end of a runner still
  there. These are the runner's WMI, CIM and window queries, the finally's `Foreign-Electron` read and its
  `results.json` write. None of them is an effect.
- **Unreadable `powershell.exe` processes.** An unrelated `powershell.exe` started after the preflight whose command
  line or executable cannot be read (for example an elevated one) makes the runner's end unproven. It also keeps QA
  from signalling the runner. This fails closed: it is a release blocker. If a runner is still live in that case, only
  the app's exact cleanup stops its effects.
- **Synchronous filesystem stalls.** A synchronous filesystem call on `/mnt/c` that hangs in the kernel cannot be
  interrupted by the single-threaded wrapper. Size, count and time checks bound every ordinary case. `run-status.json`,
  written first, keeps the outcome, and the 10 s headroom is the margin. The parses, ledger, stringify and report write
  after the last time check also rely on that headroom.
- **Unverified on Windows:**
  - how WSL interop delivers SIGTERM and SIGKILL;
  - whether the Windows command line matches the exact invocation (a mismatch yields "unresolved", a release blocker);
  - the spawn-to-creation gap;
  - every ceiling, none of which has been measured.
- **Claude Bash, from the tool metadata only.** The foreground timeout defaults to 120 000 ms, with a maximum of
  600 000 ms. Detaching is forbidden for required work.
- **Still natively unverified (unchanged):**
  - the overlay predicate;
  - cross-process affinity reads;

  - decision latency;
  - the 16-entry holding ceiling;
